# Architecture and safety invariants

## Scope and trust model

The implemented authority chain is:

```text
read-only platform/display/runtime capability probes -> DoctorReport v1
one HTTPS URL -> side-effect-free WebAppOnboardingPlan v1 (legacy) or v2 (bundled shell)
confirmed onboarding -> exact manifest/install/profile -> WebAppOnboardingResult v1/v2
strict AppManifest -> descriptor-relative AppStore
explicit runtime-lock v1 -> retained-fd verification -> RuntimeIdentity v1
checked-in GeckoRuntimeSourceLock v1 + five explicit offline Mozilla inputs
  -> signed-checksum/hash/source-metadata/tar verification
  -> normalized archive-exact GeckoRuntimeCandidate v1
candidate descriptor + retained distribution directory + immediate tree revalidation
  -> direct package-relative candidate test execution
checked-in ChromiumRuntimeSourceLock v1 + explicit Arch CEF package/signature
  + exact Arch packaging checkout + bundled CEF shell source
  -> package-signature/metadata/tar + packaging/SDK/toolchain verification
  -> exact single-job shell build + normalized ChromiumRuntimeCandidate v1
candidate descriptor + retained runtime directory + installed sandbox revalidation
  -> sealed-config CEF Views reference-shell execution
manifest + verified runtime -> sentinel-marked managed profile
exact definition/runtime/profile state -> WorkflowStatus v1
optional external capability or verified package bundle + derived policy
  -> App Shell inspection/status v1/v2/v3
exact install or repair -> versioned workflow result
exact existing binding + retained runtime/profile descriptors
  -> inert LaunchTicket inspection
  -> explicitly confirmed supervised process
optional App Shell execution
  -> retained adapter fd + sealed policy fd + pre-content ACK pipe
  -> privileged permission/WebRTC/download mediation + downstream picker/portal boundary
  -> supervised process
immutable Discord acceptance requirements -> BenchmarkScenario v1
strict local host/runtime/phase/check evidence -> BenchmarkResult v1
scenario + result -> deterministic BenchmarkAcceptance v1
DiscordConformanceSuite v1 + RuntimeDriverDescriptor v1/protocol v2
  -> explicit test-only semantic channel + current-Zen supervisor in isolated cgroup
  -> closed DiscordConformanceTranscript v1 + cgroup-v2 samples
stable CgroupSample v1 + exact coarse Gecko process-role evidence
  -> PID-free aggregate GeckoMemoryAttribution v1
```

LaunchPlan/Desktop output is an inert description boundary. Runtime identity attests only the exact opened local file. Profile markers bind a private container to exact inputs. A launch ticket is deterministic evidence, not replayable authority; execution reacquires and verifies the binding while retaining the relevant descriptors.

This slice has been exercised with fake runtimes, a qualified local native Zen 1.21.15b executable, the archive-exact official Firefox 154.0 candidate, and the signed-package-derived Arch CEF 151.3.24-1 candidate with its exact project shell. Neither candidate assembler discovers or downloads inputs, and the package contains no browser archive/tree, Arch package/SDK/candidate, or generic Firefox/Chromium certification. Session-specific display choice is intentionally absent from manifests, runtime locks/identities, profile markers, launch plans, Desktop previews, Gecko/Chromium source locks, and candidate descriptors.

The independently versioned contracts are manifest schema v1; WebAppOnboardingPlan/Result v1 for legacy and v2 for bundled App Shell; launch-plan v1; runtime-lock/identity v1; GeckoRuntimeSourceLock, GeckoRuntimeTree, and GeckoRuntimeCandidate v1; ChromiumRuntimeSourceLock, ChromiumShellSourceTree, ChromiumSdkTree, ChromiumRuntimeTree, ChromiumRuntimeCandidate, and ZenCefShellConfig v1; doctor-report v1; workflow-status v1, external-App-Shell v2, and bundled-App-Shell v3; app-install/repair v1/v2/v3; AppShellPolicy, AppShellAdapterCapability, AppShellAdapterProtocol, and AppShellHandshake v2; AppShellMediationRequest and AppShellMediationDecision v1; external AppShellInspection v1 and bundled inspection v2; launch-ticket v1; explicit-display launch-ticket v2; browser-adapter-bundle v2; BenchmarkScenario, BenchmarkResult, BenchmarkEnvironment, and BenchmarkAcceptance v1; DiscordConformanceSuite, DiscordConformanceTranscript, and DiscordConformanceReport v1; RuntimeDriverDescriptor v1; Runtime Driver wire protocol v2; RuntimeDriverSessionPlan v1; and GeckoProcessRoleEvidence and GeckoMemoryAttribution v1. Unknown fields, duplicate keys, missing fields, and unsupported versions fail closed where JSON authority is parsed. Future schema changes require explicit migration rather than silent reinterpretation.

## Manifest, modes, extensions, and links

`Opaque` and `Transparent` remain presentation requests at the manifest/legacy boundary. Bundled App Shell v2 consumes the mode only after its identical privileged security chrome, parent mediation, and remote-content boundaries are active. `Transparent` requests an alpha-capable top-level XUL/browser surface; it does not apply fractional opacity to the root and therefore does not dim descendants. Neither mode may weaken TLS indicators, permissions, sandboxing, Fission/process isolation, download protections, or security controls.

The extension catalog is metadata only. Zen Internet is marked bundled and Stylus may be selected, but each entry has `codeIncluded: false`; arbitrary IDs, URLs, paths, metadata, and extra fields are rejected. Plans report selected extensions as `unsupported`, and no extension package is included, resolved, downloaded, or executed. Separately, the privileged adapter contains one reviewed, hash-pinned Discord USER_SHEET adapted under MIT from Zen Internet's `my-internet` commit `f3a6453942894205c8644c5b0aefb502706a462e`. It is eligible only for app ID `discord`, exact start origin `https://discord.com`, and `Transparent` mode, and its own `@-moz-document` rule repeats the exact HTTPS-origin scope.

Manifest v1 fixes link policy to same-origin internal navigation, external-by-default delegation, and no user weakening. Legacy launch still reports this as `requested-not-enforced`. Bundled App Shell checks canonical scheme/host/effective port at top-level request start and committed location, including redirects; same-origin HTTPS remains internal and ordinary cross-origin HTTPS is stopped before a privileged external-handler confirmation. A cross-origin target becomes an authentication candidate when a recognized callback parameter resolves to the app origin or an origin already pinned in the current authentication chain. A callback-free account-enrollment target may also become a candidate, but only after a pinned authentication origin has committed, when source and target share the app's registrable domain and the target path contains the exact segment `signup`, `sign-up`, `register`, or `create-account`; eTLD lookup failures and every unrelated path or site fail closed. Privileged confirmation pins only that exact HTTPS origin for the current flow, every additional origin requires confirmation, and return to the app origin clears all session pins. Custom protocols require their own confirmation. Popups, protocols, downloads, federated multi-provider authentication, permissions, spoofing, and accessibility still need a broader browser-automation matrix before production completeness is claimed. Website content never controls the privileged rule.

## Inert plan and Desktop boundaries

`launch_plan.py` takes explicit absolute runtime, launcher, and profile-root strings and derives `PROFILE_ROOT/APP_ID` lexically. It neither resolves nor creates those paths. Its argv is a token array, never a shell command. Rendering is sorted, indented JSON with one LF and no PID, fd, timestamp, random value, probe, network access, or subprocess.

`desktop.py` prints a preview only. `Exec` invokes the explicit launcher with `plan`; token quoting follows Desktop Entry syntax, controls are rejected, and literal percent signs are doubled. The preview uses `Terminal=true`, generic `application-x-executable`, and `X-Zen-App-Runtime-Plan-Only=true`, with no StartupWMClass, D-Bus activation, MIME claim, XDG discovery, or live file installation.

## Descriptor-relative storage invariants

- App IDs are lowercase ASCII slugs and are the only active-definition filename input.
- Store paths are validated in their original lexical form and must be absolute. Walks begin at `/` using no-follow, close-on-exec directory descriptors. Existing ancestors are root/effective-user owned and not group/world writable.
- Store roots are exact mode 0700; active definitions are effective-user-owned mode-0600 regular files with one link.
- Creation validates before mutation, synchronizes canonical bytes into unnamed `O_TMPFILE`, and publishes from the retained fd with `linkat(AT_EMPTY_PATH)`. It re-reads and constant-time compares bytes and verifies owner/mode/size/inode/link count before success.
- Reads are bounded, reject duplicate JSON keys, and compare descriptor identity before/after.
- Removal uses no-replace atomic quarantine, verifies against the retained validated descriptor, truncates and synchronizes that inode, and never unlinks a post-validation pathname. A successful operation leaves a strict zero-length mode-0600 tombstone. Listings ignore only the exact safe tombstone grammar and shape.
- Plan/Desktop/inspect reads do not create a missing store. Removal is exact-ID and requires `--yes`.

Corruption, policy weakening, unknown schema, unsafe ownership/modes, hard links, symlinks, rebinding, or unexpected entries fail closed.

## Pinned local runtime boundary

Runtime-lock v1 contains exactly `runtimeLockVersion` and `runtime.path`/`runtime.sha256`. Paths must be explicit, absolute, lexically normalized text; empty, `.`, `..`, doubled-leading-slash, and control-character components are rejected. JSON is duplicate-free UTF-8 and bounded to 65,536 bytes.

Verification requires Linux/POSIX descriptor-relative primitives including `O_NOFOLLOW`, `O_DIRECTORY`, and `O_CLOEXEC`. Every ancestor and lock/runtime file is owned by root or the effective user and not group/world writable. The runtime is a regular readable file executable by the effective user. SHA-256 is streamed from its open fd; full `fstat` identity is compared around reads/hashing and the digest is constant-time compared. RuntimeIdentity v1 contains only normalized logical path and verified digest.

Verification performs no discovery, execution, subprocess, network request, download, update, signature substitution, or lock generation. If an OS package entry point is a wrapper, the lock must identify the exact intended executable rather than trusting the wrapper to resolve an unverified target.

## Offline Gecko candidate boundary

`runtime_candidates/gecko-firefox-154.0-linux-x86_64-en-US.lock.json` is canonical GeckoRuntimeSourceLock v1 and is independently pinned in Python by SHA-256 `037cd82a1e840ab5734a5fa54263bf62c07bc53e5d058512b2211e1030f9db3b`. It contains no local path. It pins Firefox 154.0 BuildID `20260812182057`, `mozilla-release` revision `9ce1ee6baeb9a3c326dbd180bdece65d8fc2eadc`, target/locale, release URLs, all five input sizes and SHA-256 values, runtime/source SHA-512 values, Mozilla primary/signing fingerprints, signature date/timestamp/algorithms/UID, the exact runtime executable, and canonical tree count/bytes/digest. A future-build toolchain snapshot is recorded, but `source.buildStatus: not-performed` and `source.reproducibilityStatus: not-tested` are mandatory v1 values.

Assembly is an explicit operator action, never part of app launch. All lock and input paths must be absolute and are walked from `/` without following symlinks. Inputs must be safe single-link regular files and remain open throughout assembly. The assembler hashes each fd, uses a private temporary `GNUPGHOME`, imports only the hash-pinned `KEY`, invokes tokenized `/usr/bin/gpg`, and accepts exactly the pinned `GOODSIG`/`VALIDSIG` signing subkey, primary fingerprint, timestamp, RSA/SHA-512 algorithms, and UID. The signed `SHA256SUMS` must contain the exact runtime and source paths/digests. No trustdb result substitutes for the pinned fingerprints.

The source tar is never extracted. The official release archive contains no `.hg_archival.txt`; its hash-pinned `sourcestamp.txt` is therefore the revision authority and must exactly match the binary `application.ini` BuildID/SourceRepository/SourceStamp. Every member is streamed and restricted to regular files/directories below `firefox-154.0` (plus its safe `.` root marker); links, specials, absolute names, controls, and traversal fail closed. The two version files and `config/milestone.txt` must also resolve to `154.0`. The runtime tar is stricter: exactly 53 regular 0644/0755 files below `firefox/`, no encoded directories/links/specials, total `329408396` bytes, and canonical GeckoRuntimeTree v1 SHA-256 `52c63263f1488d75ea0819138fad02c23edad360e1396751ee3c957fd960c2b0`. Extraction is entry-by-entry through retained directory fds with `O_EXCL`; `extractall()` is never used. File/directory modes and mtimes are normalized, data and directories are synchronized, and `renameat2(RENAME_NOREPLACE)` publishes only a missing output.

The output root contains only `gecko-runtime-candidate.json` and `firefox/`. The closed, canonical, privacy-bounded descriptor repeats deterministic provenance and runtime identity but no cache/output path, user, host, PID, profile, or measurement. Verification rejects any unknown root entry, malformed descriptor, mode/mtime change, hard link, symlink, special, empty/unknown directory, byte/tree mismatch, source-lock mismatch, or logical/runtime-directory rebinding. A retained distribution-directory fd yields `/proc/self/fd/N/firefox`, preserving package-relative resources that would be broken by a single-executable memfd snapshot.

Descriptor retention and immediate re-hashing close pathname replacement and pre-spawn tampering. They do **not** prevent another same-UID process from changing files inside an effective-user-owned open directory after the final check. Such assembled trees are development/bakeoff authority only. Release step #15 must stage the selected tree root-owned and non-user-writable (or supply equivalent immutable mount/content-addressed authority) before production use.

The runnable candidate is bit-for-bit derived from Mozilla's signed official binary archive. The matching signed source archive and revision are provenance only: no local Firefox source build, source-built binary equality, clean-builder comparison, SBOM, or source-build reproducibility PASS is claimed by this step.

## Managed profile boundary

The profile root is explicit, absolute, normalized, and descriptor-walked without symlinks. New roots are mode 0700 with exact mode-0600 `.zen-app-runtime-root.json`; an existing root lacking that canonical sentinel is never adopted. Each app profile is exactly `PROFILE_ROOT/APP_ID`, mode 0700, with exact mode-0600 `.zen-app-runtime-profile.json` binding normalized root, app ID, manifest schema/digest, and full RuntimeIdentity v1.

The authoritative provision API verifies the supplied runtime-lock itself. A caller-created RuntimeIdentity is not accepted as proof. Exact existing markers return `status: existing`; every mismatch or unsafe object fails closed. Marker publication uses synchronized unnamed-fd bytes and `linkat(AT_EMPTY_PATH)`, then verifies bytes/metadata and directory-entry identity. Pre-commit interruption enters descriptor-relative rollback; rebound replacements are not deleted. Failures after publication or committed synchronization report durability uncertainty rather than success.

There is no managed-profile deletion, adoption, force, migration, root discovery, Firefox initialization, or access to `~/.mozilla`, `profiles.ini`, or another default/existing browser profile.

## High-level doctor and app workflow boundary

`app onboard URL` is a network-free terminal onboarding boundary over the existing authorities. URL syntax is canonicalized locally to credential-free HTTPS with lower-case IDNA host and default port removal; path, query, and fragment remain part of the exact start URL. No title, icon, manifest, redirect, or other remote metadata is fetched. The default display name comes from the first meaningful host label. The default app ID is a bounded host slug plus ten lowercase SHA-256 hexadecimal characters over the entire canonical URL, keeping different paths on one origin distinct while remaining within manifest v1's 64-character grammar. User overrides still pass the strict manifest validators.

WebAppOnboardingPlan/Result v1 remains deterministic legacy behavior: it records the exact manifest, normalized authority paths, display request, legacy browser experience, requested actions, and `confirmation: required`; confirmed launch uses normal stock chrome and reports `inBrowserAppShell: false`. Selecting `--bundled-app-shell` instead emits plan/result v2 and records `bundled-privileged-app-shell` plus `policy-fd-and-pre-content-handshake`. Preview remains side-effect-free even if the lock/store/profile is missing. Confirmed onboarding verifies runtime and the closed adapter before definition/profile mutation, then uses the same exact manifest. Both paths are idempotent; app-ID collision and invalid runtime fail before overwrite.

Terminal confirmation and browser onboarding are separate gates. `--yes` authorizes local definition/profile creation and process execution; bundled mode then maps trusted browser-chrome onboarding with the site still unloaded. Only its enabled confirmation control calls `loadURI(startUrl)` after the parent has accepted the adapter ACK. Omitting `--bundled-app-shell` never implies these browser properties.

`doctor` is a read-only orchestration layer over platform, display, and optional runtime authorities. DoctorReport v1 contains `overallStatus: ready|blocked`, independent `/proc/self/fd` and sealed-runtime-snapshot platform statuses, explicit/automatic display resolution, and runtime `not-requested|verified|invalid`. Verified runtime reports whether execution would use a `sealed-snapshot` or `trusted-root-file`. The sealed-snapshot probe uses a temporary anonymous memfd and closes it; it creates no persistent file, store, profile, process, or network side effect.

`app status` reads an exact existing definition and delegates to runtime/profile/display verification without provisioning. WorkflowStatus v1 distinguishes runtime `verified|invalid`, profile `ready|blocked|unchecked`, display `legacy-v1|available|unavailable`, and aggregate `ready|blocked`. Invalid runtime authority makes profile status `unchecked` rather than implying a meaningful profile verification. Omitting display policy reports `legacy-v1`; explicit `auto|wayland|x11` uses the same one-snapshot resolver as launch-ticket v2. `app inspect` deliberately returns the exact launch ticket, not a workflow wrapper.

For doctor/status, exit 0 means a valid ready report, exit 1 means a valid blocked JSON report, and exit 2 is reserved for parse/input/safety errors. Other successful workflow commands return 0 and authority/precondition failures return 2. This keeps operational readiness machine-readable without weakening fail-closed input handling.

`app install` validates its manifest and runtime lock before store mutation. It then either exclusively publishes a missing definition or byte/model-equivalently accepts the exact existing definition; any difference fails closed without overwrite. Profile provisioning remains delegated to the authoritative provisioner. If profile provisioning fails after definition publication, the valid definition intentionally remains as repairable state. `app repair` reads that exact definition and idempotently provisions its profile/runtime binding. `app launch --yes` checks confirmation before store access, then delegates to the existing supervised execution authority.

There is no unsafe workflow uninstall. The low-level definition `remove --yes` does not delete a managed profile and is not presented as app uninstall. There is also no runtime discovery, automatic trust, download, update, lock generation, profile adoption/deletion, default-profile access, or persistent display selection in this workflow.

## App Shell policy, capability, and startup boundary

AppShellPolicy v2 is deterministic and derived from the already strict manifest. It requires custom onboarding before site content without default-profile import; hidden sidebar/tab strip/free-form address bar; revealable minimal security chrome with available origin and permission indicators; same-origin navigation decided at final top-level commit including redirects; external-by-default popups; confirmation for custom protocols; deny-unless-pinned authentication callbacks; exact privileged permission/download mediation; app-specific window identity; and no normal additional browser windows. The bundled adapter realizes an authentication pin as an in-memory, exact-origin set created only by privileged confirmation. A recognized callback parameter must prove a return to the app or an already pinned authentication origin, except for a callback-free enrollment hop from an already committed pinned origin: that narrower case additionally requires source and target to share the app's registrable domain and an exact enrollment path segment. The set is never persisted and is cleared on return to the app origin.

Shortcut policy v2 is closed rather than user-extensible. Reload, find, print, zoom, Escape, Alt+F4, Discord `Ctrl+K`, and Discord `Ctrl+Shift+N` remain content-visible/available. Alt+Left/Right are remapped to same-origin history, Ctrl+L to the origin/security panel, and Ctrl+W to close the app. Normal browser tab/window/private-window/address/fullscreen/devtools combinations remain blocked. Privileged handling wins over content; OS/compositor-reserved combinations are explicitly outside browser interception. `Opaque` and `Transparent` may alter presentation only after the same security chrome contract is active.

AppShellAdapterCapability v2 remains the external-adapter path: bounded duplicate-free JSON, no-follow absolute descriptor walk, exact RuntimeIdentity binding, and exactly ten capabilities (`download-mediation-v2`, `file-picker-boundary-v1`, `minimal-security-chrome-v1`, `navigation-policy-v1`, `onboarding-v1`, `permission-mediation-v2`, `shortcut-policy-v2`, `startup-handshake-v2`, `wayland-screencast-portal-v1`, and `window-identity-v1`). It is an operator claim, so status reports only `ready-for-startup-handshake` and actual execution still requires the v2 ACK. `--bundled-app-shell` is mutually exclusive and replaces the claim with local code authority: `browser_adapter.py` expects exactly eight paths, hashes every bounded regular non-executable single-link file through no-follow retained descriptors, rejects unknown tree entries, checks browser-adapter-bundle v2 canonical tree SHA-256 `3dbc0f9459b3aaf0daa1a1b32a00c531e70f9aa3e593f482c57ae23ed039e45a`, and re-hashes immediately before spawn. Bundled status/install/repair are v3 and inspection is v2.

The adapter bundle is `application.ini`, two chrome manifests, `shell.xhtml`, `shell.css`, `shell.js`, `discord-zen-internet.css`, and `defaults/preferences/prefs.js`. Gecko 154 loads privileged `chrome://zenappshell/content/shell.xhtml` via `-app /proc/self/fd/ADAPTER_FD/application.ini`. The shell owns branded pre-content onboarding, top-edge-revealable floating origin/security chrome, controlled authentication/external dialogs, an initially empty content-browser host, controls, shortcut capture, global additional-window observation, optional closed-authority site theme registration, and fatal UI. The security surface overlays content and is hidden by default, so it consumes no page layout height; the top-edge handle and `Ctrl+L` keep it available. `Transparent` keeps the XUL root, stack, browser host, and eventual remote browser backgrounds transparent without changing root opacity. For the exact Discord policy, `nsIStyleSheetService` registers the origin-scoped theme as a USER_SHEET and propagates it to future remote content processes before the ready handshake; the sheet is unregistered on shell teardown. Other opaque web content may still cover the alpha channel. No remote browser or web-content process is created during onboarding. Startup order is closed policy read → exact schema/canonical-byte check → optional pinned theme registration → global handler installation → SHA-256 → handshake write/close → confirmation enable. Only a later user action creates the transparent remote browser, attaches its popup and top-level progress listeners, and then loads `startUrl`.

`app_shell_mediation.py` defines privacy-bounded AppShellMediationRequest/Decision v1 evidence. Canonical request bytes bind a random opaque token to the exact policy SHA-256, canonical HTTPS origin, document incarnation, navigation epoch, sorted closed kind set, transient-activation fact, and a 30-second monotonic expiry. Exactly one request may be outstanding. Decisions bind the request hash, require a trusted privileged activation for any non-denial, are session-only with `persistence: none`, and cannot claim downstream picker/portal consent. Screen capture can only deny or produce `continue-to-portal`; downloads/file pickers require the system picker. Canonical policy is not a pipe payload in bundled mode. The URL is absent from child argv; bundled mode adds adapter-directory, policy-read, and handshake-write descriptors plus only the two explicit fd-number environment variables. ## Launch tickets and display resolution

Omitting `--display-backend` preserves the exact historical LaunchTicket v1 type, canonical JSON bytes, and legacy child-environment behavior. Explicit `--display-backend auto|wayland|x11` creates DisplayLaunchTicket v2. V2 adds exactly:

```json
"displayBackend": {
  "requested": "auto|wayland|x11",
  "resolved": "wayland|x11"
}
```

All common logical fields remain deterministic: runtime identity, manifest digest, profile path, fixed argv, and sanitized child environment. Tickets contain no PID, descriptor number, inode, timestamp, random token, or `/proc/self/fd` path.

Display resolution takes one snapshot of the supplied/ambient environment during ticket construction:

- `auto` prefers valid Wayland, then valid X11. If Wayland variables are present but malformed, resolution fails closed instead of silently selecting X11.
- Wayland requires `WAYLAND_DISPLAY` to be a safe basename and `XDG_RUNTIME_DIR` to be absolute and lexically normalized. V2 authors `GDK_BACKEND=wayland` and `MOZ_ENABLE_WAYLAND=1`, and removes `DISPLAY`/`XAUTHORITY`.
- X11 requires a nonempty `DISPLAY`; optional `XAUTHORITY` must be absolute and lexically normalized. V2 authors `GDK_BACKEND=x11`, removes `WAYLAND_DISPLAY`, and does not inherit arbitrary `MOZ_*` forcing.

Missing/unsafe declarations fail before launch side effects. Session display choice is ephemeral and never changes persistent authority. `launch inspect` verifies the exact profile/runtime binding but remains read-only: no mkdir, lock, subprocess, network, discovery, or store creation.

## Supervised execution boundary

`launch execute` requires `--yes` before store access or mutation. The authoritative context retains the exact hashed runtime, profile, and root descriptors. It creates/validates this effective-user-owned mode-0700 layout relative to the retained profile descriptor:

```text
PROFILE/.zen-app-runtime/{home,cache,config,data,state,tmp}/
```

A single-link mode-0600 `.zen-app-runtime-launch.lock` is opened relative to the profile and held with nonblocking exclusive `flock` until the original launch session has no live members; concurrent launch fails immediately. Launcher-managed entries require exact type, owner, mode, link count, and descriptor/path identity.

Runtime execution authority depends on mutability. A root-owned executable that the non-root effective user cannot modify remains on the original retained descriptor, preserving package-relative Zen resource discovery. An effective-user-owned executable is copied in the same loop that computes the lock digest into an anonymous mode-0500 memfd, then `F_SEAL_WRITE|F_SEAL_GROW|F_SEAL_SHRINK|F_SEAL_SEAL` is applied and read back. Missing Linux memfd/seal capabilities fail closed. Immediately before spawn, the chosen authority's metadata, digest, and—when applicable—seal mask are revalidated.

The deterministic legacy logical argv remains `RUNTIME --no-remote --new-instance --profile PROFILE_PATH START_URL`. It is not the ephemeral execution argv: `Popen` loads `/proc/self/fd/RUNTIME_FD` via its `executable` parameter, preserves logical runtime argv[0], substitutes `/proc/self/fd/PROFILE_FD` for the actual profile, and rewrites only fixed HOME/XDG/TMP values below that profile fd. Legacy execution passes exactly runtime+profile descriptors. Both opt-in App Shell paths remove `START_URL` from the actual child argv and add policy-read plus handshake-write descriptors. External mode relies on the separately verified capability; bundled mode also retains the adapter directory and inserts `-app /proc/self/fd/ADAPTER_FD/application.ini`. Only the policy/handshake descriptor numbers are authored into the sanitized child environment, and the serialized base ticket remains fd-free. The lock/root/parent and opposite pipe ends remain private. Thus a Popen-boundary runtime source mutation cannot alter the sealed image and a profile pathname rebind cannot redirect the child's profile or launcher-owned state.

`Popen` uses a token array, `shell=False`, `close_fds=True`, and `start_new_session=True`. The parent inherits stdout/stderr and forwards SIGHUP/SIGINT/SIGQUIT/SIGTERM to the launch session. Direct-leader signal status maps to 129/130/131/143. If the leader exits with same-session live groups, bounded TERM then KILL draining occurs before descriptors and the profile lock are released; zombie-only members are not executing authority. Cleanup failure raises rather than reporting success. This is process-session supervision, not cgroup containment: a malicious pinned runtime that deliberately creates a new session is outside this guarantee. There is no normal detached mode.

The child receives fixed safe PATH plus a reviewed GUI/session allowlist; host HOME/PATH, `LD_*`, `PYTHON*`, arbitrary `MOZ_*`, and unknown variables are excluded. This is not a substitute for Firefox/Zen content sandboxing, seccomp, NoNewPrivs, Fission, Safe Browsing, TLS/permissions UI, or exploit mitigations; upstream protections must remain enabled.

After confirmation, the site committed in a remote web content process with `Seccomp=2`, `NoNewPrivs=1`, `-sandboxReporter`, and `-chrootClient`, then supervisor exit 143 and an empty original runtime session. The site URL was absent from child argv and the actual profile remained fd-backed.

The local D-Bus session currently exposes `org.freedesktop.portal.Desktop`; ScreenCast reports interface version 6, `AvailableSourceTypes = 7`, and `AvailableCursorModes = 3`, while FileChooser reports version 4. These values prove service/interface availability only. The native camera, microphone, speaker, shared-audio, download Save-picker, WebRTC-indicator, and actual screen-source portal-consent workflows were deliberately not exercised: no device was opened, no portal source was selected/captured, no restore token was produced, and no screenshot was taken. Their end-to-end status is `not exercised`/`incomplete`, not PASS. Live Discord conformance is also unrun without an account/test fixture.

## Future integration points

1. Expand privileged browser automation to cover redirect chains, popup-created and multi-provider/federated authentication, protocols, permissions, downloads, spoofing, shortcut priority, and accessibility on Wayland and X11.
2. Either remove the exact-Zen custom-application `resource:///` compatibility warnings without importing unpinned code, or define and verify a separate companion-resource authority before supporting more runtime versions/layouts.
3. Resolve catalog extensions only to reviewed pinned distribution artifacts with explicit consent.
4. Add signed/offline-verifiable upstream/source/build locks and provenance if browser code is imported.
5. Test pure Xorg and additional explicitly pinned package formats/versions before claiming them.
6. Wire the cgroup-v2 collector through Runtime Driver v2 and controlled workload orchestration so every BenchmarkResult phase is populated without reducing sandbox/Fission/process isolation.
7. Design a signed atomic updater with rollback only after a dedicated threat model.
